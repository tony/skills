# Language and project-type exceptions

Use this reference only for the relevant context. A language does not determine the README audience: a Rust repository may ship a CLI, a Python extension, a library, or source for contributors. Apply the ecosystem checks and the project-type checks separately. Examples below are observed patterns at pinned snapshots; verify current versions and policies before changing an active project.

## Ecosystem checks

| Trigger | Verify or preserve | Do not import into unrelated READMEs |
|---|---|---|
| Python package, especially a native extension | Distribution name versus import name; interpreter and wheel support versus source-build tools; optional imports used by the first example; return types and migration differences. [orjson][orjson] makes its bytes-return behavior explicit. | Rust/compiler setup for wheel users; optional NumPy or other framework setup as a universal prerequisite. |
| JavaScript/TypeScript library | Runtime and module context, package manager chosen by the project, framework binding, and actual file/import consistency. [NanoStores][nano] deliberately changes its naming advice for Svelte. | Node assumptions in an embedded JS runtime; one framework's naming or lifecycle conventions in another; multiple equivalent package-manager commands in one runnable block. |
| Rust crate or executable | Whether the reader needs a Cargo dependency, a binary installation, or a complete project; features, toolchain limits, and cleanup when relevant. [Ratatui][ratatui] connects a scaffold to a complete terminal lifecycle. | Source-build tooling in every binary user's path; stripped-down examples that leave a terminal or resource in a changed state. |
| C/C++ library | Language-standard, compiler, platform, ABI/linkage, and build-system facts that affect this integration. [OpenTelemetry C++][cpp] distinguishes the tested matrix from expected portability and links examples with build files. | Every compiler flag in the landing page; equating a CI matrix with proof of all possible supported environments. A short portal such as SDL can route setup elsewhere. |
| JVM/Kotlin/Scala library | Artifact coordinates, version compatibility, Gradle DSL/source set, backend, and JDK requirements where applicable. [Kotlin MCP][kotlin] explains engine dependencies that are intentionally not transitive. http4s separates Scala compiler constraints from backend JDK constraints. | Android or multiplatform requirements in JVM-only usage; interchangeable Groovy/Kotlin DSL; assumptions that all declared dependencies provide a runnable backend. |
| .NET/F# package | Target frameworks, package choice, SDK versus runtime requirements, and conceptual helper assumptions. [FsToolkit.ErrorHandling][fsharp] exposes separate packages and Fable compatibility. | Fable's JavaScript/Python toolchains as prerequisites for every .NET consumer; a contributor build workflow ahead of the first user example without a reason. |
| Swift package | Package, product, and module identifiers; tools/platform requirements; required imports; backend selection if the package is a facade. [SwiftLog][swift] makes the facade/backend distinction visible. | Xcode-only setup for every SwiftPM consumer; treating a logging API dependency as a complete production logging configuration. |
| Go library or extension toolchain | Module versus executable installation context; supported toolchain; resource ownership in examples; cross-compilation, private modules, or generated binary location only when relevant. [Testcontainers for Go][go] states the creation/cleanup contract and routes setup to its guide. | Container prerequisites for ordinary Go libraries; an inline tutorial when a short source portal already gives a precise maintained next step. |
| Ruby tooling or gem | Ruby compatibility and the actual package/dependency route; distinguish gem installation, application dependency resolution, and library imports. [RubyGems][ruby] explains that it is normally already present and preserves the OS-managed upgrade exception. | A second installation over an OS-managed tool; replacing application-specific Bundler instructions with a generic global install. |
| BEAM/Elixir package | Mix dependency environment, formatter imports, macros, OTP/app lifecycle when relevant, and language-native abstractions. [StreamData][beam] distinguishes test-only use from formatter requirements. | Development dependencies in a consumer's production configuration; a generic dependency snippet that loses necessary environment qualifiers. |
| Julia package or registry | Package versus registry role, stable/development track, compat constraints, and actual registration requirements. [General][julia] supplies a specific disclosure policy for substantial generated contributions. | Registry maintainer procedures in every package README; deleting a required disclosure under an anti-slop rule; assuming a pinned policy snapshot is current. |

These checks identify questions, not mandatory sections. Keep details in a linked installation or reference page when the README already makes that route clear.

## Project-type checks

| Trigger | Verify or preserve | Do not generalize |
|---|---|---|
| GitHub Action | Workflow/step insertion context, required inputs, produced files, permissions, platform/runner limits, and version-specific behavior. [upload-artifact][action] explains hidden-file defaults and selected exclusions. | Remove security-relevant behavior as warning clutter; update a major version everywhere before checking server compatibility and migration semantics. |
| Terraform provider or Kubernetes operator | Consumer registry/installation route versus maintainer workflow; account/cluster requirements; resource kinds; effects of acceptance tests and development overrides. [Terraform Random][terraform] explicitly hands the README from users to developers. | Demand an inline deployment tutorial from a source portal; treat contributor tests as harmless local unit tests; require every operator to use a commercial account because one CRD does. |
| Container image or local service stack | Image registry/tag and architecture, port direction, authentication, resource needs, storage persistence, and cleanup where relevant. [Jupyter Docker Stacks][containers] explains the host port and where the token comes from. | Remove meaningful image pins; confuse host and container addresses; present a development credential or ephemeral setup as production configuration. |
| Editor or terminal plugin | Host version and mode, activation/configuration order, bindings, external tools, reload/help routes, and resource cleanup. tmux-open maps selections and keys to outcomes; rust.vim explains activation order and native help. | Standalone application instructions for a host plugin; one editor's configuration locations or one shell's syntax for all users. |
| Data, ML, or scientific software | Hardware/runtime constraints, model or data prerequisites, reproducible configuration, metric definitions, safe serialization scope, and scientific citation when applicable. safetensors defines comparison terms; NeMo RL separates independent backends; JuMP provides citation information. | Generic CPU hello-world examples that conceal the workload; arbitrary removal of tested environment pins, citations, or limitations; exact sample counts presented as expected output without a fixed fixture. |
| Font or graphic asset collection | Specimen/download route, supported formats/characters/renderers, generated-asset differences, and per-asset licenses. [Noto Emoji][fonts] distinguishes fonts, tools, and image licensing. | A code quickstart for an asset adopter; flatten multiple licenses into one badge; infer rendering support from the file extension alone. |
| Documentation, runtime-source, or contributor portal | Clear repository identity; published documentation; consumer versus contributor routes; generated/imported sources; focused local build instructions for maintainers. dotnet/runtime and git-scm.com serve these different source-facing jobs. | Require every README to duplicate installation, API reference, and a tutorial; edit generated output before identifying its source. |
| UI component gallery | Preview that demonstrates the actual component, direct component docs, framework/style compatibility, and whether users install a library or copy owned source. shadcn/studio's previews fit this role. | Delete useful visuals as decoration; replace the distribution model with a misleading package-install command; preserve several paragraphs repeating the same promise. |
| Migration, recovery, or diagnostic tool | When the tool is necessary, compatibility, backup/recovery boundaries, actual file effects, and relevant data transmission. The Factorio upgrader explains when no migration is needed; Ghostty distinguishes local crash artifacts from uploads. | Remove backup or privacy facts to make the page calmer; add generic warnings where no relevant behavior exists. |
| Relocated, archived, or deprecated project | Current maintenance status and a verified replacement or continuation route. A repository whose entire job is relocation can correctly have a very short README. | Rebuild it into a fresh product landing page; preserve an apparently active demo invitation without checking its support status. |

A niche requirement belongs near the decision or action it changes. If its source is uncertain, flag verification rather than inventing a compatibility matrix, installation step, warning, or policy. Preserve a working reader path even when a different project uses a different successful shape.
